# Ticket check — prod-deploy

1. **minor** — Spec → Runbook contents lists `terraform init` as a runbook step. No ticket's runbook checklist names it: 02 covers bucket/Atlas/keys/SSM, 04 covers first deploy/rollback/backup/troubleshooting. Add it to 03's `lld.md` item (03 creates the backend config that `init` reads).
   Related: the deploy script itself should run `terraform init` (idempotent) before the `-target` apply, or a first run from a fresh clone fails. Neither the spec's step list nor 03 says so.

2. **blocker** — 03 and 04 are `ready-for-agent`, but their "Ran it for real" items cannot be done by a subagent alone. The full `terraform apply` is interactive by design (spec → Deploy step 3: "shows the plan and waits for `yes`. That is the reviewed plan"), and the reviewer is the keeper. A subagent in a non-interactive shell either hangs, or pipes `yes` and skips the review the spec relies on. It also creates billable public AWS resources (both tickets are Risky: yes). Fix: give 03 and 04 the same Agent / Keeper split as 02 and 05. The agent writes Terraform + script and runs `fmt -check`, `validate` and `terraform plan` (plan output quoted). The keeper runs `npm run deploy`, types `yes`, and pastes the curl / smoke-check output into `## Comments`. Status: `ready-for-agent`, then `ready-for-human`.

3. **minor** — The `Status:` lines in 02 and 05 hold two values ("ready-for-agent (agent part), then ready-for-human (keeper part)"). `docs/agents/issue-tracker.md` defines one canonical value per line. The ordering itself works. In 02 the agent writes the runbook, then the keeper follows it, and 03 is blocked on the whole of 02. In 05 the keeper uses the phone, then the agent writes status. The session only has to hold between the two parts. Say so in each ticket, e.g. "Status: ready-for-agent; flip to ready-for-human when the Agent items are ticked", so `/implement` knows to stop rather than call the ticket done after the subagent returns.

4. **minor** — 02 → 03 hand-off of the state bucket name is missing. S3 names are global, and neither spec nor ticket names the bucket. 02 should record the chosen name (runbook + `## Comments`), and 03's backend block should read it from there. Same for the Atlas region note: it is fine as is.

5. **minor** — The Terraform root's path is not in the ticket or the spec, only in ADR-0012 (`infra/prod/`). A builder reading only ticket + spec would guess. Name `infra/prod/` in 03.

6. **minor** — 03 needs Terraform outputs that the spec lists only under 04, and one the spec omits entirely. 03's deploy needs the ECR repository URL (push) and the function name. Its acceptance curls the **function URL**, which is not in the spec's outputs list. Add "outputs: ECR repository URL, function name, function URL" to 03. 04 then adds the CloudFront URL, distribution id and bucket name.

7. **minor** — Spec deploy step 3 is "Builds the PWA, then full `terraform apply`". 03 rightly skips the PWA build, but 04 only says "Deploy steps 4–7", so nothing tells the 04 builder to add the PWA build into step 3. Add it to 04's deploy item.

8. **minor** — 01's `docker run` against the dev MongoDB: `.env.example`'s `MONGO_URL=mongodb://localhost:27017/...` resolves to the container itself, not the host's compose Mongo. Say `mongodb://host.docker.internal:27017/fishtank_dev` (Docker Desktop on macOS), or `--network host` elsewhere, so the builder doesn't lose time on a 503 / boot hang.

9. **minor** — 01's "image contains no `.env*`, `tickets/`, `qa/`, `infra/`" check lists the final image. A multi-stage build that copies only `build/` + `node_modules` passes it trivially even with a bad `.dockerignore`. The thing the spec cares about is the build context (secrets in `.env` sent to the daemon / build stage). Add: the build-stage layers also lack `.env*` (e.g. `docker build --target <build stage>` then list it), or check the context size/contents in the build log.

10. **minor** — Story 12 (rollback by deploying an earlier commit) is written in 04's runbook but never exercised. 03's "second run on the same commit" covers re-deploy, not rollback. Either add "deployed the previous commit from a throwaway worktree, smoke check passed, then redeployed HEAD" to 04 (keeper part per finding 2), or accept it as untested and say so in the ticket.

11. **minor** — 04 is the largest ticket, near the limit for one context: S3 + OAC + bucket policy, CloudFront with two behaviours + CloudFront Function, deploy steps 4–7 with a nine-assertion smoke check, five runbook sections and `hld.md`. Not a blocker, since each part is spelled out in the spec. If it needs slimming, move the backup and troubleshooting runbook sections to 05's Agent part. They aren't needed before first use, while the "sign up straight away" and lost-race sections must stay in 04 because 05's keeper follows them.

12. **minor** — 03's "a second run on the same commit succeeds (mutable tag)": with an unchanged tag, `image_uri` is unchanged, so Terraform won't update the function. That's fine for the same commit, and the item only proves the push isn't rejected. Worth one line so the builder doesn't "fix" it by forcing an update or adding a digest.

Checked and fine: Blocked-by edges (01 and 02 parallel; 03 ← 01, 02; 04 ← 03; 05 ← 04) match the real dependencies. Labels (pattern / boilerplate / new design) fit. Test seams match spec → Testing Decisions (local `docker run`, function URL health, CloudFront smoke check, phone acceptance). Every user story 1–24 maps to a ticket. ECR lifecycle (20), log retention (21), state lock (23) and secrets by hand (13, 14) are in 02/03, and status (24) is in 05. No spec item is built twice: `lld.md` is touched by 02, 03 and 04 but in different sections. Health route returns `database: connected` as 01 and 03 expect. `GET /api/v1/me` and `POST /api/v1/auth/register` exist for the smoke check and 05's sign-up-closed check.
