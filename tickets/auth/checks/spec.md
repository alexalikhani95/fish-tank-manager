# Spec check: tickets/auth/spec.md

- **minor** — Only the 401 body is pinned ("same error envelope as validation errors"). The 403 (closed sign-up), 409 (duplicate email) and 400 for `PATCH me` with an empty body ("at least one field" — which field does the error name?) have no stated body, so tests can only assert status. Fix: state that 401/403/409 all use the existing envelope with a fixed message/code each, and say what `PATCH me {}` returns (e.g. a form-level error with no field, or `field: null`).
- **blocker** — Contradicts ADR-0006 (and `hld.md` → Auth): the CSRF defence there is "`SameSite=Lax` **plus** the API accepts `application/json` only, no form-encoded endpoints". `app/config/bodyparser.ts` still parses `application/x-www-form-urlencoded` and `multipart/form-data`, and the Zod schemas would happily accept `email=…&password=…` or a form-encoded `PATCH me`. This spec is what makes cookie auth live, so it is where that premise has to become true, and it says nothing. Fix: add a decision "the API parses JSON only — drop the `form` and `multipart` parsers from `config/bodyparser.ts` (multipart is not needed: photos go straight to S3)", or a check that rejects a non-JSON body on mutating routes, plus one Seam 1 test (a form-encoded `auth/login` is not a 200 and sets no cookie).
- **minor** — The cookie's test shape is unstated, and the Japa helpers won't work with a bare JWT. `@japa/plugin-adonisjs` `withCookie` **signs** the value, `withPlainCookie` base64-**encodes** it, and `response.cookie()` runs Adonis's cookie parser, which won't read a raw `eyJ…` value. A test that "logs in and reuses the cookie" in the obvious way gets a 401. Fix: say that tests read the raw `Set-Cookie` header and send `.header('cookie', 'token=<jwt>')`, and that the middleware reads the cookie unencoded (e.g. `request.plainCookie('token', { encoded: false })` or the raw header). Then the tests check the flags: `HttpOnly`, `Secure`, `SameSite=Lax`, `Path=/`, `Max-Age=2592000`, no `Domain`.
- **minor** — `Secure` is not in the config default. `config/app.ts` sets cookie `secure: app.inProduction` and `maxAge: '2h'`, so a `response.cookie(...)` that leans on the defaults ships without `Secure` in dev/test and with a 2-hour life. Fix: say the auth cookie passes every attribute explicitly (`secure: true` in every environment, `maxAge: '30d'`, `domain` unset) and doesn't rely on `config/app.ts`.
- **minor** — Cookie vs bearer precedence is ambiguous when both are present and the cookie is bad: "reads the cookie first, then falls back to Bearer". Does an expired cookie plus a valid Bearer get in, or get a 401? Fix: state one rule, e.g. "the cookie is used if present, else the header; there is no retry with the other", and keep the two Bearer tests cookie-less as written.
- **minor** — The name of the ctx property for the User is not given ("puts the User on the request context"). ADR-0009 says "on `ctx`, not `ctx.auth.user`", and `ctx.userId`'s `declare module` lives in `current_user_middleware.ts`, which is being deleted. Fix: name it (e.g. `ctx.user: UserDocument`, set alongside `ctx.userId`) and say the `HttpContext` augmentation moves into the new auth middleware file.
- **minor** — The 401 / 403 / 409 bodies only say "the same error envelope as validation errors". That envelope is `{ errors: [{ field, message }] }`, and nothing says what `field` is for a non-field error, while the Tanks 404 uses a different shape (`{ message }`). Fix: pin each one, e.g. `{ errors: [{ field: '', message: 'Unauthorized' }] }` (same as the handler's whole-body rule), and do the same for 403 `Sign-up is closed` and 409, so tests can `deepEqual` the identical-401 cases (story 10) instead of only comparing status.
- **minor** — Story 10's "same error" is only testable if the bodies are byte-identical. Fix: the login test asserts the wrong-password and unknown-email responses are `deepEqual` (status and body), which depends on the item above.
- **minor** — The User's API shape `{ id, … }` doesn't match Tanks, which go out as raw Mongoose JSON (`_id`, `__v`, `userId`). Two id spellings in one API will bite `web/`. Fix: either give User a `toJSON` that also returns `_id` (drop only `passwordHash`, `tokenVersion`, `__v`), or state that `id` is the API convention now and the Tanks shape changes too (with its tests). In both cases the `GET me` test checks the exact key set.
- **minor** — Register/login strictness isn't stated. `PATCH me` is strict, but "register and login share the same schema" doesn't say whether an unknown key (`{ email, password, role: 'admin' }`) is a 400 or silently stripped (the Tank create schema strips). Fix: state it, e.g. non-strict and stripped like `createTankSchema`, or strict.
- **minor** — The 409 path can't be tested through the agreed seams. The 403 check runs first, so a duplicate email needs two concurrent first sign-ups, and the Testing Decisions don't list it. Fix: say it is not tested (accepted, like the race), or name a deterministic way (e.g. two parallel `register` calls with the same email on an empty DB, expecting one 201 and one of 403/409).
- **minor** — The test reset is "each group starts from empty `users` and `tanks`". Per group would chain tests through closed sign-up (test order matters). Also, dropping the collection would delete the `email` unique index, which Mongoose won't rebuild mid-run. Fix: "each **test** starts from empty `users` and `tanks` (`group.each.setup` + `deleteMany`, never `drop`)", as `tanks.spec.ts` already does.
- **minor** — The revoked-token and deleted-User 401 cases don't say how the test sets them up, and "no unit tests of internals" could be read as forbidding model access. Fix: say the setup may use the model directly (`User.updateOne({ $inc: { tokenVersion: 1 } })`, `User.deleteOne`), as the ownership test already does for its second User. Otherwise the revoked case goes through Seam 2.
- **minor** — `user:set-password` leaves several things open. (a) Is the `<email>` argument trimmed and lowercased like the API's (story 6)? `Me@Example.com` should find the User. (b) Is the email checked before or after the prompt? That decides whether the test traps a prompt for the unknown-email case. (c) A single hidden prompt with no confirmation turns a typo into a password the keeper doesn't know (story 27 "can't lock myself out"). Fix: normalise the argument with the same Zod email rule, look up the User before prompting, and ask twice ("New password" / "Confirm password"), exiting non-zero on a mismatch. Also give the exact prompt texts so the test can `prompt.trap(...)` them.
- **minor** — The command needs wiring the spec doesn't name. It must set `options.startApp = true` (Mongo + `hash`), the test imports it but `package.json` has no `#commands/*` alias, and `hash` needs `@adonisjs/core/providers/hash_provider` in `adonisrc.ts` as well as `config/hash.ts` (the spec only says "its config comes back"). Fix: list these three in Implementation Decisions.
- **minor** — `JWT_SECRET` wiring is incomplete. The spec removes `DEV_USER_ID` from `.env.example` and `.env.test` but never says to **add** `JWT_SECRET` to both. The expired-token test needs it in `.env.test`, and a developer's local `app/.env` stops booting until it's set. Fix: add `JWT_SECRET=` (with a "≥ 32 chars, e.g. `openssl rand -base64 48`" comment) to `.env.example`, a fixed 32+ char value to `.env.test`, and a note to update local `.env`.
- **minor** — Story 31 (refuse to start without a strong `JWT_SECRET`) has no test and isn't in either seam. Fix: say it's verified by hand (boot with a 31-char secret and with none, and see it fail) and record that in the PR, or accept it as untested.
- **minor** — Story 15 (logout with an expired cookie) has no listed test, though it's cheap: Seam 1 can send the expired JWT the test already builds. Fix: add "logout with an expired/tampered cookie → 204 and cookie cleared" to the Seam 1 list, and allow that as a second place the hand-built expired token is used (the spec currently says it's the _only_ place).
- **minor** — The design-doc update list misses stale lines. `hld.md` line 75 (Validation: "Registration closes behind `REGISTRATION_OPEN`") and line 23 ("PWA … Holds the JWT", wrong since ADR-0006). `lld.md`: Status codes line (add 403 closed sign-up, 204 logout), Ownership check (`auth.user.id` → `ctx.userId`), the "Password minimum 12" rule (now 12–256), and the `@adonisjs/auth` line under Framework wiring. `PLAN.md`'s Auth item still says "custom JWT guard (ADR-0003)" and "`REGISTRATION_OPEN`", so it should be reworded as well as ticked. `docs/status.md`'s Product plan row still lists "ADR-0002 to ADR-0007". Fix: add these to the Design docs bullet.
- **minor** — The agreed step "throw away the test tanks in your local database" is only a Further Note ("wiping is fine"), not an action anyone does. Fix: make it an explicit step (e.g. `db.tanks.deleteMany({})` on `fishtank_dev`, or drop the database) in the ticket that removes `DEV_USER_ID`.
- **minor** — Vocabulary: CONTEXT.md says to avoid "Account" (use User), yet the Solution and stories 1, 3, 16 and 19 use "account", and Implementation Decisions say "on their account". Fix: say "User" in the Solution and Implementation Decisions (stories may keep the keeper's voice), or add "account" to CONTEXT.md if it's meant to be a term.
